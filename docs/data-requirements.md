# Требования к хранению, обработке и использованию данных

Сводка требований к данным EcoDB. Исходное ТЗ — `TZ_BD_specialist_reviewTM.docx`. Пункты с пометкой «согласовать» ещё не утверждены заказчиком.

## 1. Хранение

| Требование | Значение |
|---|---|
| СУБД | PostgreSQL 14 + PostGIS 3.4 (`docker-compose.yml`) |
| Схема | `eco`, версии через `sql/migrations/NNN_*.sql`, журнал `eco.schema_migrations` |
| Кодировка | UTF-8, русский язык в наименованиях, комментариях и значениях |
| Геометрия | `GEOMETRY(Point, 4326)`, WGS84. `NULL` допустим до получения каталога координат |
| Среды мониторинга | `air`, `surface_water`, `groundwater`, `soil`, `vegetation` |
| Глубина истории | не менее 5 лет по всем объектам и лабораториям |
| Сырые данные | строки источника хранятся без изменений в `eco.staging_lab_import` с `batch_code`. Исходные файлы — в `DB_input/` |
| Справочники | показатели, точки, лаборатории, нормативы и синонимы (`parameter_aliases`, `point_aliases`) — единственный источник ПДК. ПДК из файлов лабораторий не используется |
| Объём | сейчас ~3 тыс. результатов и ~50 МБ станционных файлов по Оскемену. Размер сервера — `docs/server-requirements.md` |
| Резервное копирование | согласовать: ежедневный `pg_dump` базы `eco_monitoring`, хранение копий не менее 30 дней, копия вне сервера БД, проверка восстановления раз в квартал |
| Срок хранения | согласовать: результаты и сырые строки staging хранятся бессрочно, исходные файлы партий не удаляются |

## 2. Обработка

Загрузка идёт только через staging. Порядок и правила — `docs/ops-handover.md`, раздел «Дозагрузка новой партии».

| Требование | Как выполняется |
|---|---|
| Форматы источников | Excel (.xlsx), CSV, PDF-протоколы для сверки |
| Партии | у каждой загрузки свой `batch_code`, состав и дата партии фиксируются |
| Преобразование | `eco.fn_process_staging_import(batch_code)`: маппинг кодов точек, показателей и лабораторий, разбор «<0.001» и «не обн.» в `less_than` / `result_value`, приведение единиц к `parameters.unit` |
| Повторный запуск | идемпотентен: повтор по паре (проба, показатель) обновляет `results`, дублей нет |
| Ошибки | неразобранные строки остаются в staging с `process_error`, `processed_at IS NULL` |
| Превышения | триггер `trg_check_exceedances` при INSERT/UPDATE `results`. После смены нормативов — `eco.fn_recalc_all_exceedances()` |
| Контроль качества | `etl/phase4.py`: сверка партий, обязательные поля, дубли, единицы, выбросы, выборка 5% против протоколов. Каждому результату присваивается код QC A/B/C/D/R. Подробно — `docs/qaqc-checks.md` |
| Сверка объёмов | расхождение источник/БД не более 0,5% без объяснения в отчёте (`docs/qa_phase4_report.md`) |

## 3. Использование

| Потребитель | Доступ | Данные |
|---|---|---|
| Администратор / ETL | пользователь `eco`, чтение и запись | вся схема `eco` |
| ArcGIS Enterprise (дашборды, Field Maps, Experience Builder) | пользователь `eco_gis`, только `SELECT` | четыре представления как Query Layer |
| Аналитики | только чтение, пример — `notebooks/query_ecodb.ipynb` | представления и таблицы схемы `eco` |

| Представление | Назначение |
|---|---|
| `eco.vw_results_flat` | все результаты с точкой, показателем и кодом QC |
| `eco.vw_exceedances_summary` | превышения нормативов: кратность и процент |
| `eco.vw_latest_results` | последний результат по точке и показателю, без кодов QC `D` и `R` |
| `eco.vw_water_levels` | уровни подземных вод |

Требования к использованию:

- У каждого представления уникальный `objectid` и столбец `geom` (EPSG:4326).
- Запрос к `vw_results_flat` за произвольный период по одному объекту — не более 3 секунд на полном объёме истории (`sql/verify_phase5.sql`).
- Для отчётности и публикации используются только результаты с кодами QC `A`, `B`, `C`.
- Пароли стенда (`eco`, `eco_gis`) меняются до промышленной эксплуатации. Adminer в продуктиве закрыт или доступен только из внутренней сети. Роли и права доступа — отдельный документ (согласовать).
